# Interview Notes

这份文档用于候选人自检。每项内容都应能结合代码、测试和实际修改过程独立解释。

## 三分钟项目说明

1. 项目是什么：一个 Godot 卡牌 RPG，包含战斗、锻造、城市/NPC、委托、高塔、音频和 AI GM，同时有一个 TypeScript 权威服务端原型。
2. 主要工程问题：玩法系统多、状态联动复杂；生成式文本又存在网络、费用和不可控输出问题。
3. 客户端方案：按战斗、锻造、世界、NPC、高塔和状态边界拆分服务，内容尽量数据驱动，并用大量 Godot 回归测试锁定跨系统行为。
4. AI 方案：用 `PromptContext` 限制输入，用 `AIGMService` 编排缓存、预算、Provider 和降级；模型只产生文本，不能绕过确定性规则。
5. 服务端方案：协议验证、会话状态、限流、AOI、快照和战斗锁分层，管理面默认关闭。
6. 证据：能够从公开仓库运行完整 Godot 测试、Vitest/TypeScript 构建和 WebQA，并解释一次具体故障的定位与修复。

## 应能从代码回答的问题

- `GameState` 为什么是共享边界，哪些状态不应由 UI 直接修改？
- 一张卡牌从 JSON 到战斗结算经过哪些对象和服务？
- 锻造的符号、反应、道心选择和最终卡牌结算如何解耦？
- 城市机会、NPC 委托和公告板为什么容易出现状态不同步，测试如何覆盖？
- 高塔 Boss 失败后撤退路径如何保持楼层与结算状态一致？
- BGM 如何按场景路由，缺少 SFX 时为什么不会崩溃？
- `PromptContext.to_dict()` 为什么要复制结构化状态？
- 哪些 AI GM 场景允许缓存，缓存键为什么不能保留原始组合标识？
- 哪些网络错误允许重试，为什么 4xx 不重试？
- 模型文本为什么不能直接修改权威状态？
- 服务端协议验证、会话状态、限流和管理鉴权分别解决什么风险？
- 如果加入 Agent 工具调用，怎样设计工具 schema、权限确认、幂等键、回放和审计？

## 项目边界

- 当前不是通用 Agent 框架，不具备任意工具规划和长期向量记忆。
- Provider 列表不代表所有模型都已接通；真实网络默认关闭。
- TypeScript 服务端是可测试原型，尚未成为当前离线客户端的必需后端。
- 运行时美术与 BGM 已进入仓库，但生成过程和额外截图不属于交付。
- 测试数量本身不是质量结论，应能解释关键用例覆盖的行为和失败原因。

## 诚实说明工作方式

- 项目使用 AI 辅助生成和修改过部分代码与美术。
- 不应声称“全部代码都是独立手写”。
- 应重点说明本人参与的需求拆解、方案选择、结果筛选、调试、测试、脱敏和发布审计。
- 面试前应能关闭 AI，独立运行测试、定位失败、解释关键模块并完成一个小改动。
