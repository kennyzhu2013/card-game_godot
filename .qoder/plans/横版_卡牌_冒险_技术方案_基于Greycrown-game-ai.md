# 固定人物横版卡牌冒险游戏技术方案

## 一、结论与设计范围

推荐技术组合：

**Godot 4＋强类型 GDScript＋纯数据战斗内核＋命令／事件协议＋AnimatedSprite2D／AnimationPlayer＋JSON 内容配置＋本地版本化存档。**

本次确认的调整：
- 卡牌模型改为固定人物：角色开战时已经在场，通过技能卡释放技能，不再通过角色卡生成单位。
- 首版平台延续 PC 单机优先，首先交付 Windows x86_64 离线版本。

本方案采用以下首版默认规则作为实施基线：
- 我方为固定三人小队，职责分别为前位护卫、中位输出、后位支援；首版只有这一套阵容，冒险及战斗中均不替换成员。
- 节点式冒险，战斗为左右对峙的固定站位，不包含横版跑跳、自由走位、战中换位或碰撞判定。
- 三人共享牌组、手牌与每回合能量；技能卡绑定所属角色，战术卡由队伍使用。
- 玩家手动出牌，结束回合后未行动角色自动普攻，随后敌方按预告意图行动。
- 我方三人对一至三个敌人；取消独立指挥官，按一侧全部倒下判定胜负。首领占一个敌方站位，不拥有额外的指挥官层。
- 首版不做角色召唤、撤回、增援、战中复活和动态扩容；固定人物不等于不能播放前冲、受击和死亡动画。
- 先完成一章可重复游玩的流程；复杂 NPC 社交、污染、契约、多人、开放世界和生成式剧情均不进入首版关键路径。

这是拟议架构，不代表当前仓库已经具备固定三人队伍、统一命令、完整战斗快照或确定性回放。相比旧方案，本次减少的是动态部署及卡牌生成角色的生命周期，保留规则与表现分离、确定性和可靠恢复的要求。

## 二、技术选型与取舍

| 层面 | 采用方案 | 原因与边界 |
|---|---|---|
| 引擎 | Godot 4；首个复现基线固定为仓库已有验证记录的 4.6.2 | 利用当前 GDScript、场景和数据积累；引擎及导出模板固定同版，不将其宣称为最新版本 |
| 渲染 | Compatibility，逻辑分辨率 1280×720 | 满足横版 2D；优先兼容集成显卡；16:9 等比缩放，超宽屏首版使用留边 |
| 语言 | 强类型 GDScript | 当前项目迁移成本低；模块边界用明确的数据类型，不让 Dictionary 无限制传遍系统 |
| 战斗计算 | RefCounted 数据对象与普通规则服务 | 不依赖 SceneTree、节点坐标、物理、动画和真实时间，可 headless 执行 |
| 人物表现 | AnimatedSprite2D＋AnimationPlayer＋Tween | 帧动画负责人物动作，AnimationPlayer 编排动作段，Tween 负责位移与界面反馈 |
| UI | Control、Container、CanvasLayer | 手牌、目标选择、状态条和弹窗使用 Godot 原生 UI |
| 内容 | JSON 为规则内容唯一来源；加载后转换为类型化对象 | 适合批量编辑、校验与现有数据迁移；媒体场景及纹理仍使用 Godot 资源 |
| 存档 | 本地 JSON 快照、双代检查点、版本迁移 | 无需数据库和账号服务器；能够恢复战斗及冒险事务 |
| 测试 | 规则层保留当前 Godot headless 测试协议；玩家流程与界面以窗口模式运行、模拟真实输入的界面测试验收 | 不为更换测试框架重写旧测试；headless 只用于纯规则，界面相关结论必须来自窗口模式运行 |
| 发布 | Windows 导出包，Git＋CI 固定构建环境 | 首版不启动现有 TypeScript 服务端；以后再评估 Steam 等发行接口 |

### 为什么不优先换 Unity、Phaser 或 C++
- Unity 能完成目标，但当前没有必须依赖其生态的功能，迁移会丢失现有 Godot 投入。
- Phaser 适合浏览器优先项目；现在是 Windows 单机、2D 场景和动画优先，没有充分理由更换技术栈。
- 首版每场最多六个主要战斗实体（三名队员＋三个敌人），不需要为计算性能引入 C++、ECS 或多线程规则系统。
- 首版不用 Spine 等第三方骨骼运行时；先用帧动画建立美术规范。若以后换表现方案，只替换 UnitView，不能影响战斗规则。

## 三、先确定可实现的战斗规则

### 3.1 固定阵容与目标选择

战场的逻辑结构：

```text
我方：后位支援 中位输出 前位护卫  →  ←  前位敌人 中位敌人 后位敌人
                         下方为共享手牌
```

- BattleSetup 根据固定队伍和遭遇配置一次性创建全部角色；正式冒险我方为三人，敌方为一至三人。开发测试允许从一对一开始。
- 站位是逻辑 slot_id，不由人物当前像素坐标决定。队员在本次冒险中的站位不变，首版不提供部署、换位或替补操作。
- 角色倒下后退出可选目标和行动集合，保留实体记录及原 slot_id 供日志与演出使用；该位置在本场保持空缺，其他人不自动前移，也不能补员。
- 普攻和近战技能攻击目标侧最前方存活角色；前位倒下后，中位成为最前方合法目标，后位同理。
- 远程技能可指定任意存活敌人；治疗与护盾按 TargetRule 选择存活队友；群体技能选定阵营后自动覆盖全部合法目标。
- 不使用 CharacterBody2D、寻路或碰撞命中判断攻击是否合法。角色前冲、退回和受击位移都是表现，不改变 slot_id。

### 3.2 两种卡牌与共享牌组

| 类型 | 效果 | 资源消耗 |
|---|---|---|
| 专属技能卡 | 由绑定的固定队员发动攻击、治疗或控制等技能 | 消耗共享能量及该角色一次行动机会 |
| 公共战术卡 | 队伍使用抽牌、护盾、治疗或能量等效果，无所属执行角色 | 消耗共享能量；不占角色行动机会 |

原型参数固定为：
- 起始牌组共 20 张卡牌实例：每位队员 5 张专属技能，共 15 张，加 5 张公共战术。允许同模板多张，内容模板数量与牌组实例数量分别统计。
- 每回合能量重置为 3，不累计；能量效果可使当前能量超过 3，但单回合上限为 6，超出部分不生效且事件记录实际增量。
- 每个 RoundStart 抽 5 张（上一回合手牌已在 EndTurn 全部弃置，因此等价于抽至 5 张）；手牌上限 8。抽牌效果在手牌已满时停止抽取，未抽的牌留在 draw 原位，不进弃牌堆、不烧牌，事件记录请求数与实际抽取数。
- 技能费用以 1–2 为主，战术费用限定为 0–3；费用及升级后变化必须通过校验。
- 卡区为 draw、hand、resolving、discard、exhaust、disabled。resolving 仅在命令事务中暂存正在结算的牌，稳定检查点必须为空；不设置角色留场卡区。
- 出牌成功后进入 discard；带本场耗尽标记的卡进入 exhaust。回合结束未使用手牌进入 discard。
- 抽牌堆为空时，仅将 discard 按 deck RNG 洗入 draw；exhaust 和 disabled 不参与。可抽卡不足时少抽，不生成补牌。
- 每张战斗卡使用独立 card_instance_id；同模板两张牌可以分别使用，但共享其所属角色的行动机会，不会生成额外角色。
- 开局采用普通确定性洗牌与抽牌，不再保证角色卡入手。三名队员开战即在场，即使没有可用技能，也可以结束回合让未行动角色普攻。

以上是用于原型验证的起始数值，不是已验证平衡的最终设计。

### 3.3 角色行动与技能归属

- 每个 RoundStart 将存活角色 action_points 重置为 1，第一回合也适用；不存在召唤当回合不能行动的限制。
- 专属技能通过 actor_unit_id 绑定角色定义，初始化时解析为唯一的 owner_entity_id。不能让其他队员代放技能，也不能把卡牌执行者误当成技能目标。
- 使用技能需同时满足：所属角色存活、未眩晕、有行动机会、能量足够且目标合法；成功后扣除该角色 1 点行动机会。
- 已经使用技能的角色不会在回合末再免费普攻；技能被拒绝或取消目标选择不消耗能量、行动机会或卡牌。
- EndTurn 先弃置剩余手牌，再进入 PlayerAutoActions。按该阶段开始时的速度降序建立队列，同速度按实体创建序号排序；每次执行前重新检查存活和行动资格，并选择当前最前方存活敌人。
- 自动普攻消耗 1 点行动机会但不消耗能量。无合法目标则跳过；EnemyActions 也按阶段开始时速度降序、同速创建序号排序，执行预告意图并消耗行动机会，跳过不消耗技能冷却。敌方同样每轮最多一次行动，首版不提供额外行动或 haste 状态。
- 技能设计必须考虑“消耗能量＋放弃普攻”的机会成本，依靠提前击杀、远程选目标、控制、治疗或群体效果提供价值。M2 试玩需验证只用战术并等待普攻不会成为压倒性的最优策略。

### 3.4 角色倒下与专属卡禁用

- hp 降至 0 时角色倒下，alive 变为 false、action_points 清零，不能行动或接受普通治疗，也不能重新入场；首版无战中复活。
- 倒下时在同一事务内清除该角色的 block、全部 StatusState 与冷却，并为每个被清除的状态生成 StatusExpired（reason=owner_defeated）；倒下角色身上的毒／灼烧不再触发，也不再产生伤害事件。敌方同样适用。
- 将该角色在 draw、hand、discard 中的专属卡按固定卡区及区内顺序移入 disabled，记录 owner_defeated 原因；不立刻补抽手牌。
- 若该角色在自己技能的反伤或连锁中倒下，当前 resolving 卡的已提交行动继续完成，结束后该卡进入 disabled，优先于通常的弃牌／耗尽去向。
- 已在 exhaust 的卡保留原区，不重复搬移；公共战术卡不受单个队员倒下影响。不存在从其他区域再次抽到该角色专属卡的路径。
- disabled 是本场禁用区，不删除 OwnedCard。下一场从 RunState.deck 重新构建所有战斗卡；只要所属队员已按战间规则恢复，该角色的卡即可重新参与抽牌。
- 成员倒下及其专属卡移区属于同一行动事务，必须与伤害、连锁事件一并保存，不能由 UI 在演出结束后补做。

### 3.5 敌方与胜负

- 玩家采用共享抽牌与能量系统；敌方由遭遇配置提供开局阵容和技能意图，不要求与玩家对称地抽牌，不在战中生成新敌人。
- 敌方普通单位和首领共用 CombatantState、效果处理、目标校验及行动执行器；首领占一个站位，可搭配最多两个护卫。
- 敌方在玩家行动前展示本轮 EnemyActions 将使用的技能与目标；玩家操作后不重新规划更有利的技能。
- 敌人在 PlayerMain 中被眩晕时，意图保持原技能但标记为 skipped，规则生成 IntentChanged（reason=stunned），UI 将意图显示为“跳过”；预计伤害归零。
- 目标死亡或不再符合目标规则时，单体技能按公开的“目标侧前位到后位取第一个合法目标”重定向；自身技能不改选他人，群体技能执行时收集合法目标，无合法目标则跳过。
- 意图锁定技能与原目标，不锁死最终伤害；执行时使用当前属性和状态，UI 更新预计值，但伤害预览不推进 RNG。
- 我方三人全部倒下判负；全部敌人倒下且至少一名我方队员存活判胜。首领倒下但仍有护卫存活时战斗继续。
- 同一行动连锁结算后双方均无存活角色，按玩家失败处理；单个队员倒下不立即结束战斗。
- 首领阶段转换不作为独立机制：首版首领只通过意图条件（如“hp ≤ 50% 时优先使用某技能”）改变行为，不更换模板、不回满生命、不追加单位。若后续需要真正的多阶段首领，另立规则与存档版本。

### 3.6 回合状态机与状态时点

```text
BattleSetup
  → RoundStart
  → EnemyIntentPreview
  → PlayerMain
  → PlayerAutoActions
  → EnemyActions
  → RoundEnd
  → 下一轮 RoundStart 或 BattleEnd
```

- BattleSetup 按我方、敌方以及各侧前位到后位的固定顺序创建实体，完成卡牌归属绑定；无效阵容、重复成员、缺失技能所有者或零生命入场配置必须拒绝初始化。
- 护盾按阵营在“拥有方下一次己方行动阶段开始时”清除：我方 block 在 RoundStart 清除，敌方 block 在 EnemyActions 开始时清除。这样敌方在 EnemyActions 中获得的护盾可以覆盖玩家下一轮的出牌与普攻，我方在 PlayerMain 获得的护盾可以覆盖本轮敌方行动，两侧护盾都能实际生效。
- RoundStart 依次清除我方旧护盾、恢复双方行动机会、结算回合开始状态并检查胜负；战斗仍进行时再重置玩家能量和抽牌。毒和灼烧的本阶段伤害统一批次应用后处理倒下，避免遍历顺序影响同归于尽。
- PlayerMain 只接受出牌和结束回合命令。EndTurn 内部完成自动普攻、敌方行动、RoundEnd 和下一轮开始，遇到胜负立即停止后续阶段。
- 每个原子行动及其连锁结算完成后检查双方存活数量，不能强制等到整轮结束。RoundStart 状态结算也遵循这一规则。
- 速度只用于同一侧自动行动的排序，不引入 ATB、真实时间进度条或额外 Tick 战斗模式。
- 状态采用独立 StatusState，不共用含义模糊的 duration：毒／灼烧每次施加生成一个含整数伤害和 remaining_triggers 的实例，在未来 N 次 RoundStart 触发并递减；多个实例伤害相加。
- 虚弱使造成的伤害乘以 75%，易伤使承受的伤害乘以 125%，按此顺序分别向下取整，再由护盾吸收。重复施加不叠倍率，剩余次数取较大值。
- 虚弱／易伤不按 RoundEnd 计时，而以 remaining_phases 表示“还会影响几个完整的生效阶段”。玩家阶段指 PlayerMain＋PlayerAutoActions，敌方阶段指 EnemyActions：
  - 虚弱影响“造成伤害”，生效阶段是受影响方自己的行动阶段，在该阶段结束时递减；
  - 易伤影响“承受伤害”，生效阶段是对方的行动阶段，在该阶段结束时递减；
  - 若状态是在其生效阶段进行中施加的，该阶段结束时不递减，从下一个完整生效阶段开始计数。
- 由此，敌方在 EnemyActions 中给我方施加的 1 次虚弱会作用于下一轮我方的出牌与普攻，1 次易伤会作用于下一轮完整的 EnemyActions；我方给敌人施加的同理，两侧同名状态强度一致。旧方案“施加当轮的 RoundEnd 计一次”会使敌方施加的 1 次减益在同一轮立即失效，不再采用。必须用双向测试锁定上述四种组合。
- 眩晕令下一次自动行动或敌方意图执行被跳过，并消耗该轮行动机会；眩晕期间尝试出技能只会被拒绝，不消耗眩晕。重复眩晕不叠加跳过次数，固定最多 1 次。
- 战间清除所有护盾、状态和行动机会；恢复生命与下一场入场规则见第九节。

## 四、整体架构与模块职责

```text
冒险界面／卡牌 UI／鼠标键盘
             ↓
      AdventureController／BattleController
             ↓ 完整命令
      BattleEngine：唯一规则写入入口
             ↓
      BattleState＋BattleEventBatch
          ↙                   ↘
SaveService／ReplayRunner    BattlePresenter
                                 ↓
                    角色动画、特效、音频、HUD
```

### 核心边界

| 模块 | 负责 | 不负责 |
|---|---|---|
| BattleEngine | 命令事务、行动及回合编排 | 资源加载、动画、存盘、联网 |
| BattleState | 固定阵容、技能归属、卡区、角色状态、能量、意图、RNG 状态 | 节点引用和临时 UI 状态 |
| TargetResolver | 所属角色资格、合法目标集合及前位目标规则 | 鼠标坐标、碰撞检测和角色部署 |
| EffectResolver | 伤害、护盾、治疗、状态等规则 | 播放动作和音效 |
| TriggerQueue | 连锁触发排序、深度与数量保护 | 使用 await 等待动画 |
| EnemyPlanner | 根据配置和状态生成敌人意图 | 调用大模型或修改规则对象 |
| BattlePresenter | 将事件批次转换为演出 | 决定伤害、掉落和胜负 |
| AdventureService | 固定队伍战间生命、节点推进、卡组升级、商店和奖励事务 | 直接操纵战斗里的角色节点 |
| SaveService | 校验、迁移、检查点恢复 | 自动补猜缺失的规则状态 |

只在应用装配层访问 GameState 或其他 Autoload；战斗内核使用注入的值对象。媒体缺失可以有显示降级，规则定义缺失必须拒绝启动对应内容。

新冒险以 RunState／ProfileState 为唯一持久状态来源，不与旧 GameState 双向同步金币、生命和牌组。进入战斗时构建 BattleSetup，离开战斗时由 AdventureService 幂等接收 BattleResult；战斗过程中不得直接修改局内队伍或旧存档。

## 五、卡牌、单位与数据分层

固定角色来自队伍配置，不来自卡牌。卡牌是角色的行动手段，不能把“技能卡实例”和“场上人物”当成同一个对象。

| 对象 | 生命周期 | 主要字段 |
|---|---|---|
| CardDefinition | 内容版本 | definition_id、kind、rarity、cost、actor_unit_id（战术为空）、target_rule、effects、exhaust_on_use、upgrades、text_key、presentation_id |
| CardUpgradeDefinition | 内容版本（内嵌于 CardDefinition.upgrades） | level（从 1 起）、cost_override、effect_param_overrides（按 effect 序号与参数名覆盖整数）、exhaust_on_use_override |
| OwnedCard | 玩家本次冒险／持有记录 | owned_id、definition_id、upgrade_level |
| BattleCardState | 单场战斗 | card_instance_id、owned_id、zone、resolved_cost、owner_entity_id（战术为空）、disabled_reason |
| UnitDefinition | 内容版本 | unit_id、max_hp、基础攻击与速度、标签、普攻定义、presentation_id |
| PartyDefinition | 内容版本 | party_id、三个角色定义及固定 slot_id、起始牌组配置 |
| RunPartyMember | 一次冒险 | member_id、unit_id、slot_id、current_hp |
| CombatantState | 单场战斗 | entity_id、unit_id、source_member_id（敌方为空）、side、slot_id、creation_seq、hp、max_hp、alive、block、statuses、action_points、cooldowns |
| StatusState | 单场战斗 | status_instance_id、status_id、source_id、整数参数、trigger_phase、remaining_triggers |
| RunState | 一次冒险 | seed、party_id、party_members、章节节点、金币、deck、rare_pity、待领取奖励、战斗结算记录 |
| ProfileState | 存档槽 | 已解锁卡池及起始牌组配置、完成记录 |
| SettingsState | 全局（不属于存档槽） | 音量、演出倍速、窗口模式、语言 |

约束：
- Definition 在运行中只读；升级和临时变化不能修改共享模板。PartyDefinition 决定固定三人阵容，首版不允许重复角色模板。
- OwnedCard 不直接传给伤害计算；战斗开始时生成独立 BattleCardState，通过 actor_unit_id 解析其唯一 owner_entity_id，缺失或多义归属均拒绝启动。
- RunPartyMember 的 member_id 在整次冒险中稳定，CombatantState 的 entity_id 仅在该场战斗中稳定；恢复快照时保留已有 ID，不重新分配。
- owner_entity_id 只是“谁能使用这张技能”的引用，不是卡牌生成或持有角色的链接。CombatantState 不保存 source_card_id，行动事件仍可记录造成伤害的卡牌 ID。
- UI 只通过 ID 与只读投影对应角色，不持有可直接修改的 CombatantState。
- 人物受伤只改变 CombatantState.hp；战斗结算后回写对应 RunPartyMember.current_hp，不修改 UnitDefinition 或 CardDefinition。
- 首版成长以局内卡牌升级和局外卡池解锁为主，不引入角色等级、装备或长期数值膨胀系统。
- 状态不变量包括：角色集合和 slot_id 在战中不变；每张卡恰在一个卡区；倒下成员在可循环卡区没有专属卡；存活角色行动机会只能为 0 或 1。
- 升级只做“覆盖”而非脚本：首版每张卡最多 1 级升级（upgrade_level ∈ {0, 1}），升级上限即 upgrades 的条目数；覆盖后的费用与参数同样通过费用范围和效果参数校验。BattleCardState.resolved_cost 在建卡时由定义与升级等级算出，战中不变——首版效果集合不含改费效果，因此不保留 temporary_cost；以后增加改费效果时再加字段并升 rules_version。
- 状态对象之间只用 ID 互相引用（如 BattleCardState 只存 owner_entity_id，不存 CombatantState 对象），由 BattleState 统一持有索引表，避免 RefCounted 循环引用导致的泄漏，也让深复制和序列化不必处理对象图。

### 类型化加载与序列化

Godot 4 的 JSON 解析会把所有数字读成 float，直接把 Dictionary 当作状态使用会在强类型 GDScript 中出现类型错误或整数比较不一致。因此：
- 内容 JSON 与存档 JSON 都必须经过 Schema 层：每个对象定义字段名、类型（int、string、enum、id 引用、列表）、必填与范围，加载时显式转换为 int 并拒绝带小数的整数字段、未知字段和超范围值。
- 64 位种子与 RNG 状态以十进制字符串保存（见 6.4），其余整数字段在安全范围内以 JSON 数字保存，读取时由 Schema 层转换。
- 序列化统一由各类型的 to_dict／from_dict 完成，输出键按字典序排列，供存档、回放与状态哈希共用（见 6.5）。
- 旧 SaveStore 直接把解析结果当 Dictionary 使用，新模块不复用该读取路径。

### 卡牌文本

- 卡面说明不手写数值，由 text_key 对应的模板加上效果参数生成，如“造成 {damage} 点伤害”；升级覆盖、虚弱／易伤等修正后的预计值由同一套伤害预览计算并以颜色标出变化。
- 所有界面文本使用翻译键，首版只提供简体中文，但不把中文字符串写死在脚本中，为后续多语言保留入口。
- 内容校验检查每个 text_key 存在、模板占位符与效果参数一一对应。

### 内容来源与编辑流程

- 卡牌、角色、状态、遭遇、奖励表、事件均以 JSON 为规则来源。
- Godot 场景、SpriteFrames、音效和纹理仅在 PresentationCatalog 中映射 presentation_id。
- 不同时维护“JSON 一套属性”和“.tres 另一套属性”；导出的校验产物不是第二个编辑入口。
- 启动和 CI 检查重复 ID、无效引用、费用范围、目标规则、效果参数、固定阵容与站位唯一性、技能归属及动画清单；遭遇人数不得超过三人。还需检查升级覆盖后的费用与参数、rarity 取值、text_key 与模板占位符、敌人默认技能与意图条件、事件选项的条件与效果参数、地图生成配置。
- 复杂卡牌通过 effect_id 注册独立处理器；不使用 eval，也不允许 JSON 执行任意脚本路径。

首版战斗效果集合限制为：伤害、治疗、护盾、抽牌、能量、施加状态和清除状态（冒险层效果另见 9.3）。首版状态先做毒、灼烧、虚弱、易伤、眩晕；不实现召唤、复活、换位、额外行动或任意属性修改。新增效果必须同时增加测试与表现映射。

## 六、命令、事件与确定性协议

### 6.1 命令入口

首版玩家命令只保留：
- PlayCard：card_instance_id、actor_id、target_ids。专属技能的 actor_id 必须等于已绑定的 owner_entity_id；公共战术 actor_id 为空。自身和群体目标由 TargetRule 确定性展开，命令载荷需与完整合法目标集合一致。
- EndTurn：结束玩家操作阶段。

不提供召唤、撤回或换位命令。公共信封包含 command_id、expected_revision、issuer、type、payload。引用使用稳定 ID，不使用手牌或场上数组下标。

处理流程：
1. 先检查已成功处理的 command_id：相同 ID 与相同请求内容返回原结果，不重放；相同 ID 对应不同内容则拒绝为 command_id_conflict。未处理过的命令再校验 expected_revision。
2. 校验阶段、资源、卡区、技能归属、角色存活／眩晕／行动资格以及目标；拒绝 actor_defeated、actor_stunned、actor_not_ready、actor_mismatch、insufficient_energy、invalid_target 等非法输入。
3. 在完整工作副本上结算；副本包含 RNG、ID 计数器、角色状态、各卡区及禁用原因。当前出牌进入 resolving，避免抽牌效果将自己再次抽回。
4. 处理效果、倒下、专属卡禁用和连锁，检查状态不变量；稳定检查点前 resolving 必须清空。
5. 成功后一次提交新状态、事件批次和命令结果记录；失败则保持原状态、RNG 和成功日志不变。

命令结果统一为 CommandResult：ok、reason_code（拒绝时）、new_revision、event_batch。reason_code 使用固定枚举，UI 根据枚举显示本地化提示，不解析字符串。

### 6.1.1 只读查询接口

UI 置灰与目标高亮、伤害预览、自动模拟玩家和命令校验必须共用同一份规则判断，因此 BattleEngine 另提供只读查询，不修改状态、不推进 RNG：
- get_legal_actions()：返回当前阶段所有可提交的 PlayCard（card_instance_id、actor_id、合法目标集合）及 EndTurn；不可用的卡附带与命令拒绝相同的 reason_code，供 UI 显示原因。
- preview_play(card_instance_id, target_ids)：返回各目标的预计伤害、护盾吸收、治疗、能量变化与是否致死。
- get_battle_projection()：返回供 BattlePresenter 校准用的只读投影。
命令处理的第 2 步直接调用与 get_legal_actions 相同的校验函数，测试需证明“查询判定为合法的动作提交后不会被拒绝，反之亦然”。

首版单位和牌数较少，使用显式深复制事务换取可验证性。含 RefCounted 的对象图必须逐对象克隆，不能假定 Dictionary.duplicate(true) 会克隆全部可变对象；用副本修改不影响原状态的测试锁定边界。不提前建设复杂的写时复制或回滚引擎。

### 6.2 事件用于表现和诊断

主要事件：
- BattleStarted、PhaseChanged、RoundStarted、BattleEnded。
- CardPlayed、CardDrawn、DeckShuffled（discard 洗入 draw）、CardZoneChanged、EnergyChanged。
- ActionStarted、ActionEnded、ActionPointChanged、ActionSkipped、CooldownChanged。
- DamageApplied、Healed、BlockChanged。
- StatusApplied、StatusTriggered、StatusExpired、UnitDefeated。
- IntentChanged。

ActionStarted／ActionEnded 成对出现，界定一次原子行动及其连锁；Presenter 以这对事件切分演出段，回合开始的毒／灼烧批次同样包在一对 Action 事件中（source 为状态实例）。DamageApplied 带 cause（card、auto_attack、enemy_skill、status、counter），便于飘字与战斗日志区分来源。

BattleStarted 携带固定阵容的只读初始化投影；角色倒下后的 CardZoneChanged 必须带原卡区、disabled 去向及原因。角色不通过动态生成事件入场，前冲与退回也不生成逻辑换位事件。

每条事件包含 event_seq、action_id、source_id、target_id、必要的数值变化和 presentation_id。公共战术以卡牌实例为来源，无须虚构一个执行角色。事件不得包含 Node、Callable 或纹理引用。

**命令记录意图，事件记录事实，快照记录状态。** 不要求仅凭“播放日志”就能还原全部规则内部状态，避免将动画事件流误当完整事件溯源系统。

### 6.3 避免重复重放 AI 行动

- 对外 CommandLog 只记录顶层驱动命令。
- EndTurn 内部派生的我方普攻、敌方行动和下一轮开始，由同版本规则及 EnemyPlanner 重建。
- 派生操作可以进入诊断追踪，但不能在回放 EndTurn 之后再作为独立输入重放一次。
- 自动模拟玩家也调用同样的顶层命令入口，不绕过能量、行动和目标校验。

### 6.4 随机性约束

- 使用独立 RNG 流：deck、combat、enemy、adventure、reward。
- deck、combat、enemy 的种子由 run_seed、battle_id 和固定流名确定性派生；adventure、reward 由 run_seed 与固定流名派生，贯穿整次冒险，不在换场或打开面板时重置。快照保存每条流的实际状态。
- RNG 的 64 位 seed/state 以十进制字符串保存，避免 JSON 数值精度损失。
- 不使用 Godot 的 RandomNumberGenerator，而是在 GDScript 中自实现固定算法（建议 PCG32 或 xorshift64*），并以已知种子的前若干输出作为金标准测试。GDScript 的 int 是有符号 64 位，乘法溢出、右移和取模必须按无符号语义处理，并用边界值测试锁定。这样回放结果不依赖 Godot 版本。
- 洗牌统一使用基于该 RNG 的 Fisher–Yates；“从 N 个中选一个”统一使用无偏的区间取值函数（拒绝采样），不使用 `rand % n`。
- 现有 turn_battle.gd 与 effect_engine.gd 中大量使用全局 randf／randi 与 Array.shuffle，移植效果时必须逐处替换为注入的 RNG 流，不得原样带入新内核。
- 禁止战斗内核使用全局 randf/randi、Array.shuffle、时间生成 ID、物理时序或 Node 遍历顺序决定规则。
- 血量、护盾和伤害使用整数；概率使用万分比整数，乘除顺序和舍入规则固定。
- 伤害预览读取规则并显示确定值或范围，不推进 RNG。
- 回放绑定 engine_version、rules_version、content_hash 和配置。

### 6.5 规范化序列化与哈希

状态哈希、内容哈希和存档校验共用一套规范化规则：
- 对象键按字典序输出；列表保持规则定义的顺序（卡区内顺序有意义，不排序）。
- 规则状态中不出现浮点数；整数以十进制输出，64 位值以字符串输出；字符串统一 UTF-8、LF。
- 状态哈希排除显示用字段（时间戳、显示名、预览缓存、演出进度），只覆盖 BattleState 与 RunState 的规则字段。
- content_hash 覆盖 client/data/card_battle/ 下全部规则 JSON：按相对路径排序后，对“路径＋规范化内容”逐个累加计算 SHA-256。由内容校验工具在构建期生成并写入清单，运行时启动再计算一次比对，不一致则拒绝加载该内容版本。
- 哈希算法使用 Godot 内置 HashingContext 的 SHA-256。

## 七、连锁效果与结算安全

首版只采用一种规则：**FIFO 队列＋确定性结算点**，不向内容作者暴露 INLINE／QUEUED 的自由切换。

单个效果的顺序：
1. 收集伤害前修正，按固定优先级计算。
2. 应用伤害、护盾或其他状态变化，生成事实事件。
3. 标记角色倒下，清零行动机会并退出存活集合；保留实体和原站位记录，同步禁用对应专属卡，不能只把 hp 设为零。
4. 将伤害后和倒下触发按优先级、来源创建序号、触发器序号加入队列。
5. 继续处理队列；普通反击要求来源存活，倒下触发允许引用已登记的倒下来源。已经接受的卡牌行动不会因执行者倒下而撤销，但不再开始该角色的新行动。
6. 当前行动队列完全清空、resolving 卡完成移区后检查双方存活数量，确认胜负。

补充约束：
- AOE 使用一个伤害批次计算并应用，再统一处理该批次死亡，避免数组遍历顺序改变群体伤害结果。
- 所有能修改战斗属性的操作必须经过规则入口，UI 或冒险服务不得直接扣血、加 buff。
- 一条顶层命令最多处理 512 个效果／触发节点；超限整体回滚并记录 RULE_LOOP_LIMIT，不静默丢弃后续效果。
- 首版不提供需要在连锁中途暂停并再次询问玩家的效果；目标选择在命令提交前完成。

## 八、横版 2D 表现与动画方案

### 8.1 场景组成

```text
BattleRoot
├─ BattleController
├─ BattlePresenter
├─ World2D
│  ├─ BackgroundLayers
│  ├─ SlotAnchors
│  ├─ UnitViews
│  ├─ VfxLayer
│  └─ Camera2D
└─ CanvasLayer
   ├─ PartyHUD
   ├─ SharedEnergyDisplay
   ├─ HandPanel
   ├─ TargetSelector
   ├─ IntentPanel
   ├─ BattleLog
   └─ ResultOverlay
```

UnitView 采用 Node2D，包含 AnimatedSprite2D、AnimationPlayer、血条／状态显示和特效挂点。开战时根据初始化投影创建全部 UnitView；无需将人物做成真实物理角色。

PartyHUD 显示三人的生命、状态与“可行动／已行动／眩晕／倒下”；手牌显示所属角色头像或公共战术标记，牌堆面板可查看 disabled 及原因，不提供部署或撤回按钮。

### 8.2 输入与演出流水线

输入状态为 Idle → CardSelected → TargetSelecting → Submitting → Presenting → Idle：
- 选中专属技能时自动定位并高亮所属队员，不再要求额外选择执行者；不能改选另一个角色代放。
- 单体技能选择合法目标，自身或群体技能显示确定目标后确认；无目标战术使用空目标列表。
- 目标高亮与提交校验共用 TargetResolver。提交前按 Esc 或点击取消只清除 UI 选择，不消耗任何规则资源。
- 请求被拒绝时返回选牌状态并显示原因；提交和演出期间禁止重复输入。

以输出角色的技能卡“斩击”为例：
1. UI 确认绑定角色及合法目标，提交 PlayCard。
2. 规则一次性得到扣费、行动机会消耗、伤害、倒下和卡区变化等完整结果。
3. Presenter 根据结果播放卡牌飞出、所属角色前冲和攻击动作。
4. 攻击动作命中标记到达时显示已计算的伤害、受击、音效和震屏。
5. 存活角色退回原锚点，倒下单位播放死亡动作并退场；显示专属卡禁用后，界面进入下一次输入状态。

公共战术从手牌或队伍 HUD 播放效果，不占用某个队员的行动动画；回合末普攻使用角色的共享攻击演出。动画命中标记只决定“什么时候展示结果”，不能回调规则引擎计算第二次伤害。

### 8.3 逻辑与画面状态分离

- BattleState 是权威状态；Presenter 维护单独 ViewState，按事件逐步更新可见血条和站位。
- 播放中不直接读取已经结算到结尾的状态，否则会出现人物还没攻击、血条已经扣完的问题。
- 每批演出结束后，将 ViewState 与权威状态投影校准。
- 一般行动播放期间锁定新的战斗输入；待机动画、暂停和设置不受影响。
- 支持 1×、2×、4×及跳过演出；仅改变播放速度，禁止通过修改规则计时实现倍速。
- 动画缺失或事件播放超时，使用默认动作并校准到最终投影，不能让战斗永久卡住。
- 存档不保存 Tween 进度；读档时重建最近已提交状态，不重复执行上次命令。
- Presenter 以 ActionStarted／ActionEnded 为单位编排演出段：段内事件按 event_seq 播放，段结束后校准一次 ViewState，再进入下一段。

### 8.3.1 输入与可读性

- 首版支持鼠标为主、键盘为辅：数字键 1–8 选牌、Tab／方向键切换目标、Enter 确认、Esc 取消、E 结束回合，按键在设置中可查看。手柄首版明确不支持，不在 Input Map 中预留半成品映射。
- 敌方意图同时用图标、数值和文字类别（攻击、防御、减益、增益）区分，不只依靠颜色；伤害数值使用描边字体保证在背景上可读。
- 新手引导首版采用首场战斗的固定提示序列（专属技能归属、共享能量、结束回合普攻、敌方意图），可在设置中关闭或重看，不做强制交互式教程。

### 8.4 美术生产规范

首版统一动作：idle、attack、skill、hit、death；开战直接站场，不要求召唤或撤回动画。基础受击动作可由少量帧配合位移实现，同一角色的多张技能优先复用 skill 动作并组合共享特效。

- 先选一种美术风格，统一角色脚底 pivot、面向、人物高度和挂点命名。
- 逻辑画布中人物可见高度先按约 180–220 像素校样，再依据站位和手牌布局调整。
- 每种角色至少定义 ground、hit、cast 三个挂点。
- 普攻、受击、飘字和常见法术采用共享特效，避免每张卡都要求独立动画。
- AI 生成素材仅可作为有权使用的美术来源或草稿；连续动作、轮廓一致性和切图仍需要人工整理。
- 第一阶段用占位人物完成真实动画协议，之后替换美术资源，不先批量制作尚未验证的角色。

## 九、冒险循环与成长

采用小型节点图，不在首版实现自由探索地图。

```text
新冒险 → 固定三人满血入队＋起始牌组 → 节点选择 → 战斗／事件／商店／休息
       → 战斗结果与战间恢复 → 奖励和升级 → 下一节点 → 首领 → 结算和解锁
```

首版一章设置 12 层节点，起点与首领固定，中间允许分支。可选择路径之间保持前进关系，不出现回边。

### 9.0 入口与流程界面

- Hub 增加一个“固定小队冒险”入口，进入独立的模式主菜单；不修改 Hub 原有入口和旧 GameState 流程。
- 模式主菜单：三个存档槽，每槽显示摘要（当前层数、三人生命、金币、最近保存时间）；可选“新冒险”“继续冒险”“放弃本次冒险”（二次确认）和“删除存档槽”（二次确认）。
- 战斗或地图中可打开暂停菜单：继续、设置、保存并返回模式主菜单。由于每条成功命令后都已保存检查点，“返回”不需要额外存盘，也不保存演出进度。
- 冒险结束（首领胜利或全灭）进入结算界面，展示本次层数、解锁内容后回到模式主菜单。
- 新模式使用独立的 BGM 路由键（地图、普通战斗、精英、首领、结算），复用现有 Bgm Autoload，缺失曲目时回退到现有战斗曲目。

### 9.1 固定队伍与生命继承

- 本次冒险固定三人的 member_id、角色定义和站位，战间不换人、不招募、不改变阵容。
- 胜利时，存活队员保留战斗结束生命；倒下队员在战间以 max(1, ceil(max_hp × 30%)) 生命恢复。采用整数运算并限制不超过 max_hp；这是原型数值，不是最终平衡结论。
- 战间恢复由 AdventureService 在接收胜利结果时执行一次，并与结果记录一起保存；不是战中复活，也不能在加载或重复领奖时再次回血。
- 三人全灭则本次冒险失败，不进行战间恢复。单个队员倒下不永久删除角色或卡牌，也不改变后续节点的固定阵容。
- 下一场以 RunPartyMember.current_hp 入场，清除上一场护盾、状态和禁用卡区，重建牌组并重新洗牌；不在每场开始时把全队自动补满。
- 首版非战斗事件扣血最低保留每人 1 点生命，避免另设场外全灭与复活流程；战斗仍可造成致命伤害。
- 平衡风险：倒下恢复 30% 与休息回复 30% 相同，倒下的代价几乎只有“本场少一人输出及其专属卡被禁用”。M4 必须把倒下惩罚列为专项验证，候选调整包括降低倒下恢复比例、倒下后下一场以低生命入场，或倒下时扣除少量金币；在验证前不改动基线数值。

### 9.2 节点、奖励与卡组成长

- 节点类型：普通战斗、精英、事件、商店、休息、首领。
- 地图生成使用 adventure RNG；奖励使用 reward RNG，与洗牌和伤害独立。
- 地图生成约束（由配置给出，生成后校验，不满足则用同一 RNG 流重新生成，最多重试固定次数后报错）：
  - 第 1 层全部为普通战斗，第 12 层为首领，第 11 层全部为休息；
  - 精英最早出现在第 4 层，同一路径上不连续出现精英，不连续出现商店；
  - 每条从起点到首领的路径至少包含 1 个商店和 1 个休息（不含第 11 层）；
  - 每层 2–4 个节点，每个节点 1–3 条出边，所有节点都可从起点到达且可到达首领；
  - 各类节点占比的目标区间由配置给出，用于批量生成统计检查，不作为单张地图的硬约束。
- 战斗之间保留三人的生命、金币、牌组和升级。奖励为三选一卡、金币及少量固定升级机会；仅从固定队员的专属技能和公共战术中生成候选。
- 卡牌奖励规则：
  - 卡牌按 rarity 分为普通、罕见、稀有，普通战斗、精英、首领分别使用配置中的稀有度权重（万分比整数）；
  - 三张候选卡的 definition_id 互不重复，且候选中至少包含 2 名不同队员的专属技能或 1 张公共战术，避免三张都属于同一人；
  - 已在卡组中的模板可以再次出现，不做全局去重；
  - 稀有保底：连续未出现稀有的奖励次数计入 RunState.rare_pity，每次未出现时提高稀有权重，出现后归零；计数随存档保存。
- 候选奖励生成后立即保存，不因反复开关界面重新抽取；允许跳过加卡，金币仍只领取一次。
- 休息提供“全队各恢复 ceil(max_hp × 30%) 生命，上限为各自 max_hp”或“升级一张卡”二选一。
- 商店提供买卡、移除卡和按配置数值治疗指定队员。移除操作必须保留至少 10 张卡及每名队员至少 1 张专属技能；价格、治疗量和升级上限由内容配置提供并校验。
- 局外先只解锁新卡池和同一阵容的起始牌组配置，不加入换人系统、装备、角色等级、天赋树、烙印与契约的多重养成叠加。

### 9.3 事件节点与冒险层效果

冒险层效果与战斗效果是两套处理器，不复用战斗 EffectResolver。事件节点 JSON 结构：

```text
EventDefinition: event_id、text_key、options[]
EventOption:     option_id、text_key、conditions[]、effects[]、result_text_key
```

- 冒险层效果首版限定为：gain_gold、lose_gold、heal_member、damage_member（遵守每人至少保留 1 点）、add_card（指定模板或按奖励规则抽取）、remove_card（玩家选择，遵守移除最低约束）、upgrade_card（玩家选择）。
- 条件首版限定为：gold_at_least、member_hp_at_least、deck_size_at_least，不满足的选项显示但不可选。
- 需要玩家二次选择的效果（移除、升级）作为同一事件事务的后续步骤，选择完成前事件不算结束；中断恢复时回到选择界面，已扣除的金币不重复扣除。
- 事件选择、效果结果和节点完成在一个检查点内写入，与 10.3 的奖励事务使用同一幂等规则。

### 9.4 敌人意图配置

敌人通过条件优先级、技能冷却和少量带种子权重实现。冷却在使用技能后设定，在随后每次 RoundStart 递减，只有冷却为 0 的技能可被选为本轮意图。先让意图清晰且可预测，再用自动模拟检查难度；不以复杂搜索 AI 或大模型增强敌人作为首版目标。

```text
EnemyDefinition.intents[]: skill_id、priority、weight、cooldown、conditions[]、target_rule
```

- 选择规则：在冷却为 0 且条件全部满足的意图中取 priority 最高的一组，组内按 weight 用 enemy RNG 抽取一个；没有可用意图时使用该敌人的默认技能（必须存在且无冷却、无条件）。
- 条件首版限定为：self_hp_ratio_at_most（万分比）、ally_count_at_most、round_at_least、round_mod（每 N 轮）、target_has_status。
- 意图在 EnemyIntentPreview 一次性选定技能与目标并保存；首领的“阶段”行为通过 self_hp_ratio_at_most 条件实现（见 3.5）。
- 内容校验检查每个敌人都有默认技能、条件参数合法、目标规则与技能匹配。

## 十、存档、回放与奖励事务

### 10.1 保存内容

SaveEnvelope 至少包含：
- save_version、engine_version、rules_version、content_hash。
- ProfileState、RunState、当前完整 BattleState；三人 member_id、固定站位和战间生命必须完整保存。
- 战斗实体与所属成员映射、技能 owner_entity_id、各卡区顺序、disabled_reason、alive、行动机会、状态剩余触发次数与冷却。
- 各 RNG 状态、实体与事件序号、当前阶段、敌方意图，以及本场已成功命令的 ID、请求指纹和原返回结果。
- 生成但未领取的奖励、按 battle_id 索引的结算记录（result_applied、reward_claimed）、存档 revision 和校验值。

SettingsState 单独保存在 user://fixed_party_settings.json，不进入存档槽、不参与 content_hash 与状态哈希；损坏时恢复默认设置，不影响存档加载。

每个存档槽是独立 profile；首版提供三个槽，每槽一场进行中的冒险。不将同一份货币或解锁状态拆成多个需要跨文件同时提交的账本。新模式使用 user://fixed_party_saves/，不覆盖旧 user://saves/；首版不自动迁移旧存档。

### 10.2 恢复策略

- 每条成功顶层命令结束、节点进入、战斗结果接收、奖励领取以及商店／休息／事件事务完成后生成稳定检查点；不保存半条命令或 Tween 进度。
- 每槽交替写 A／B 两代检查点：写入非当前代临时文件，flush、关闭、校验，再完成该代文件替换。
- 启动时选择校验通过且 revision 最高的一代；写入或替换失败仍可恢复上一代。
- 保存失败时，由应用协调层保留待保存结果、暂停新的战斗或冒险提交并提示重试；仅重试写入，不重跑规则、战间恢复或奖励生成。进程退出仍可能丢失这次未保存操作，界面必须明确提示。
- 不能只依赖 Windows 上“覆盖原文件的 rename 一定成功”，必须测试中断和文件占用失败路径。
- 恢复战斗必须加载已有角色 ID、生命、行动机会和卡区，不重新运行 BattleSetup；也不能把已有 disabled 卡提前放回抽牌堆。
- content_hash 只覆盖规则内容，不包含纯纹理／音频字节；不匹配时拒绝盲目恢复旧战斗，通过已测试迁移或保留相应内容版本恢复。
- checksum 用于发现损坏，不宣称能防止单机玩家修改存档。

### 10.3 战斗结果、恢复与奖励幂等

按 battle_id 区分两个原子检查点：
1. 接收 BattleResult：写入终局状态、三人战后生命与一次性战间恢复、固定候选奖励，以及 result_applied=true。若战斗结果为失败（我方全灭），则记录冒险失败且无奖励，不恢复队员；重复接收只返回原结果。
2. 领取或跳过奖励：同时写入奖励选择、金币／卡牌变化、reward_claimed=true 和节点完成状态。首领奖励完成后同时写入冒险完成与解锁；重复提交不重复发放或推进。

若终局战斗检查点已存在但 result_applied 尚未写入，启动恢复时由应用协调层从已保存终局状态重新构建同一个 BattleResult 并接收，不重新打一遍战斗。奖励领取前不得进入下一节点；休息治疗和商店交易也以稳定事务 ID 防止重复扣费或回血。

### 10.4 回放与问题复现

回放包保存初始化参数、内容版本、随机状态和顶层命令序列。ReplayRunner 使用同一 BattleEngine headless 重放，比较每条命令后的规范化状态哈希；显示时间等非规则字段不参与哈希。

初期不实现完整的观战 UI、跨版本兼容录像或网络回滚。先确保开发者能够凭一个回放包准确复现问题。

### 10.5 本地诊断

- 规则异常（状态不变量失败、RULE_LOOP_LIMIT、未知 reason_code、存档校验失败）时，自动将当前回放包、最近一个检查点和错误摘要写入 user://fixed_party_diagnostics/，按时间命名，最多保留 20 份。
- 战斗日志与演出超时也写入同目录的滚动日志文件，单文件大小设上限。
- 设置菜单提供“打开诊断目录”，便于玩家反馈问题；诊断文件不含账号或机器信息。

## 十一、当前项目和对比项目的使用方式

### 11.1 当前 Greycrown：保留外围，隔离新内核

### 11.2 Card-Combat-System：借鉴接口，不直接复制

- 卡牌定义与运行状态分离。
- 命令、事件、快照三种边界。
- 种子与 RNG 状态管理。
- 明确触发顺序、headless 模拟和异常输入测试。

## 十二、验证、性能与交付门禁

### 12.1 规则测试

必须覆盖：
- 固定阵容初始化、重复成员／站位、缺失所属角色、非法入场生命及敌人超员的拒绝路径。
- 费用不足、所属角色不匹配／倒下／眩晕／已行动、目标死亡等拒绝路径；失败后状态、RNG、卡区与行动机会完全不变。
- 第一回合直接使用技能、技能后不重复普攻、公共战术不占角色行动机会、自动行动同速度排序和动态合法目标选择。
- 同模板不同实例共享所属角色行动机会；角色倒下时各卡区专属卡禁用、当前 resolving 卡最终去向、耗尽卡保留原区、公共卡不受影响。
- 空牌堆、手牌不足、没有可用技能时仍可结束回合普攻；不补抽被禁用的手牌、不重复抽取正在结算的卡。
- AOE 同批倒下、倒下触发、反击致死、双方全灭、仅一个队员倒下、首领倒下但护卫仍存活。
- 状态触发与叠加规则、眩晕跳过行动、伤害舍入、护盾清除时点、前位倒下后的合法目标及意图重定向。
- 超限连锁回滚、深复制隔离，以及重复 command_id 的相同请求复用／不同请求拒绝。
- 护盾分阵营清除时点：敌方在 EnemyActions 获得的护盾能吸收下一轮玩家伤害，我方护盾能吸收本轮敌方伤害。
- 虚弱／易伤双向计时的四种组合（见 3.6）、手牌满时抽牌停止、能量上限、倒下时清除状态与护盾。
- get_legal_actions 与命令校验一致性：对随机生成的大量状态，查询合法的动作提交必成功，查询不合法的必被拒绝且 reason_code 相同。
- 自实现 RNG 的金标准输出、无符号运算边界值、Fisher–Yates 与区间取值的分布检查。
- Schema 层拒绝带小数的整数字段、未知字段、超范围值，JSON 往返后类型与数值不变。

### 12.2 确定性与存档测试

- 同初始化＋同命令得到相同状态哈希和事件序列。
- 在每个可保存检查点恢复，后续结果与不中断执行一致。
- 动画 1×／4×／跳过得到相同战斗结果。
- 随机种子和状态经 JSON 往返后逐位保持一致。
- 临时文件不完整、某代损坏、写入失败仍能加载上一有效检查点。
- 领奖中断后既不重复发放，也不出现节点已推进但奖励消失。
- 队员倒下后保存恢复，角色 ID、行动机会、专属卡归属与 disabled 保持一致，不重新初始化或复活。
- 胜利后的生命继承和倒下恢复只执行一次；下一场所有拥有卡重新构建，上一场耗尽／禁用不永久丢卡。
- 战斗终局到结果接收、结果接收到领奖各边界中断后可恢复；保存失败重试不重复执行行动、治疗或发奖。
- 旧存档与固定队伍模式存档互不覆盖，规则内容版本不兼容时明确拒绝加载。

### 12.3 内容与玩家流程测试

- 所有内容引用、技能所属角色、效果参数、卡池过滤和媒体映射均通过校验。
- 新档→三人固定站场→角色专属技能→公共战术→结束回合普攻→胜利→战间恢复→领奖→商店／休息→保存→恢复→首领结算。
- 专门覆盖一个队员倒下、专属卡禁用、胜利后低血恢复及下一场重新抽到该角色技能的完整路径。
- UI 集成检查实际共享能量、每人生命与行动机会、卡区和节点状态；目标取消无副作用，截图不能代替业务断言。
- 冒险测试覆盖三人全灭终止、跳过加卡、移除卡牌最低约束、重复交易和治疗上限。
- Windows 导出包进行离线启动、窗口缩放、暂停恢复和缺失可选媒体冒烟。
- 地图生成批量统计：大量种子下所有约束成立，节点占比落在配置区间内。
- 事件节点二次选择中断恢复、奖励候选稀有度与互不重复、稀有保底计数跨存档保持。

### 12.3.1 界面测试（窗口模式）

玩家流程、输入与表现的验收必须在窗口模式下运行真实场景，不以 headless 结果代替：
- 测试驱动通过 Input.parse_input_event 注入鼠标点击和按键，按真实路径完成“选牌 → 选目标 → 提交 → 等待演出 → 下一次输入”，不直接调用 BattleEngine 命令。
- 每一步断言界面实际显示值（手牌数、能量数字、三人血条与状态图标、意图图标与数值、卡区计数）与权威状态投影一致；截图只作为失败时的附加证据。
- 覆盖：目标取消无副作用、拒绝操作的提示、演出期间输入被锁定、1×／4×／跳过三种倍速、暂停菜单、存档槽主菜单的新建／继续／放弃、读档后界面与读档前一致。
- 界面测试套件与规则套件分开计数和报告，CI 在 Windows 运行器上以窗口模式执行；开发机上同样可一键运行。

### 12.3.2 自动模拟与平衡指标

- 内置三种基准策略，全部通过 get_legal_actions 与顶层命令入口行动：随机策略、贪心策略（每步选择预计伤害或有效治疗最高的动作）、只用战术卡策略（不使用任何专属技能）。
- 每次内容变更后对固定种子集合批量模拟，输出：胜率、平均回合数、每场生命损失、各队员技能使用比例、倒下次数、能量浪费率。
- M2 通过条件之一：贪心策略胜率明显高于只用战术卡策略；具体阈值在 M1 结束后根据首批数据写入本节，不提前拍定。

### 12.4 CI

当前仓库没有任何 CI 配置（无 .github 目录），此前的验证结果均为手动执行，因此 CI 需要从零搭建，作为 M0 的交付物而不是后续补充：
- 使用 GitHub Actions；规则与内容校验可在 Linux 运行器上执行，界面测试与 Windows 导出在 Windows 运行器上执行。
- Godot 4.6.2 可执行文件与导出模板按版本号固定下载地址并校验 SHA-256，缓存到运行器，不使用“最新版本”。
- 首次导入生成的 .godot/ 缓存按 Godot 版本与资源哈希缓存，减少每次导入时间。

固定引擎和导出模板版本，执行：
1. 资源导入和脚本加载检查。
2. 内容校验与 content_hash 清单比对。
3. 旧回归＋新规则、确定性和集成测试。
4. 窗口模式界面测试（Windows 运行器）。
5. 检查零测试、缺失套件和脚本加载失败，不能只信进程退出码。
6. 固定场景批量模拟及对象数量回落检查；输出平衡指标作为构建产物。
7. Windows 导出验证，并以导出包启动执行一次冒烟流程。

测试中的预期负例错误使用明确标记区分；未知脚本错误必须使构建失败。

### 12.5 性能目标

首版场景按三名固定队员、最多三个敌人、最多八张共享手牌验收，不以数百单位为目标。性能统计同时覆盖专属卡禁用、群体伤害和 EndTurn 的完整自动行动批次。

建议固定一台 i5-1135G7／集成显卡／8GB 内存级别 Windows 测试机：
- 1080p 输出目标 60 FPS。
- 常规规则命令 P95 计算时间目标小于 5ms，不含演出和磁盘写入。
- 运行内存目标低于 1GB。
- 连续 500 场固定模拟后，对象数量不出现持续增长。

这些是待测验收目标，不是当前性能结论。优化优先级为纹理尺寸、特效并发和分配热点，不提前多线程化战斗规则。

### 12.6 Windows 发布要求

当前 export_presets.cfg 的 Windows 预设中产品名、公司名、图标均为空，且 embed_pck=false。M5 前需补齐：
- 新增独立的固定小队模式导出预设（或在现有预设上补全），填写产品名、公司名、文件版本与产品版本、程序图标。
- 版本号采用 主.次.修订 格式，与 SaveEnvelope 中的 engine_version 分开维护；每次发布在构建产物中记录 Git 提交号。
- 决定是否 embed_pck：单文件分发便于玩家，但更容易被杀毒软件误报；首版建议保持 exe＋pck 分离并在说明中写明。
- 代码签名：首版若不签名，需在发布说明中告知 SmartScreen 提示及处理方式；正式上架前再评估购买签名证书。
- 导出过滤需排除 tests/ 与诊断、开发工具脚本，并在 CI 中检查导出包不含测试文件。

## 十三、分阶段实施与验收

| 阶段 | 交付内容 | 通过条件 |
|---|---|---|
| M0：可复现基线 | 固定引擎／导出版本、梳理可复用资源与许可、保护旧入口和旧存档；搭建 CI（含 Godot 与导出模板固定下载、窗口模式运行器）；Schema 层、自实现 RNG 与规范化序列化 | 干净环境导入和旧回归结果可解释；CI 能在 Windows 运行器上跑通旧回归、一个空的窗口模式界面测试和一次导出；RNG 金标准与 Schema 往返测试通过 |
| M1：无美术战斗 | 纯内核、命令、只读查询接口、卡区、固定阵容、专属技能归属、行动机会与禁用；六个测试卡模板（每人一技能＋三种战术）；三种基准模拟策略 | 无场景依赖 headless 执行，先一对一再三对三；倒下、全灭、拒绝操作、护盾与减益计时、查询与校验一致性及确定性测试通过；产出首批平衡指标并写定 M2 阈值 |
| M2：横版垂直切片 | 三名固定人物、技能演出、共享手牌、角色行动 HUD、敌人意图及两类卡交互、键盘操作、卡牌文本模板 | 一场真实可玩的战斗，并通过窗口模式界面测试；倍速／跳过不改变结果；贪心策略相对只用战术卡策略达到 M1 写定的阈值 |
| M3：冒险闭环 | 模式主菜单与存档槽、固定三人生命继承、战间恢复、节点图及生成约束、奖励规则、事件节点、商店、休息、卡牌升级、完整存档、本地诊断 | 先小型节点闭环再扩为 12 层；新档到首领可完成，并在窗口模式界面测试中走通；中断恢复、战间恢复、事件二次选择及领奖幂等测试通过 |
| M4：内容与平衡 | 三名固定角色、至少 20 个卡牌模板（每人至少 5 个技能＋至少 5 个公共战术）、6 类普通敌人、2 类精英、1 个首领 | 无占位的单章可玩版本；验证 20 张起始牌组、角色间用牌比例、倒下惩罚（见 9.1）与治疗经济 |

执行顺序：先用固定单角色验证“出牌→角色动作→结算”链路，再用三人队伍证明“专属技能＋共享能量＋角色行动”的单场战斗有趣，最后扩冒险内容。每个阶段以验收通过为前提，不用代码量或素材数量代替完成度。

## 十四、明确延后的能力与扩展边界

首版不做：角色卡召唤、战中增援／撤回／复活、动态站位、替补与招募、额外行动、实时 PvP、联机合作、账号服务器、云存档、战斗回滚、开放世界、复杂永久养成、MOD 脚本执行及在线 AI 剧情。

后续扩展方向：
- 更多固定角色：先评估开局选队、技能卡池过滤与生命继承，再增加可选阵容；不是首版必须支持的自由组合。
- 召唤或换位玩法：另立规则设计，增加实体生命周期、目标与卡区协议及存档版本迁移；不能只增加一个动画或效果处理器就宣称兼容。
- 移动端：替换输入布局、调整资源预算，复用同一个规则内核。
- 更复杂人物动画：替换 UnitView 和 PresentationCatalog，保留事件协议。
- 在线叙事：在战斗及奖励提交之后异步生成文本；超时离线降级，不能修改规则或阻塞行动。
- 联网战斗：另立项目评估权威协议。可考虑由现有 TypeScript 网关管理会话，Godot headless 运行同一规则内核；不能把本地可序列化命令直接当成已安全的网络输入。

## 最终建议

先建设一个“小而完整”的产品：**固定三人小队＋角色专属技能卡＋公共战术与共享能量＋清晰敌人意图＋单章节点冒险**。

技术重点依次是：**固定阵容与技能归属、角色行动和倒下卡区处理、规则与表现分离、确定性及完整恢复**。先从固定单角色验证，再扩三人协作；保留现有项目可用的外围成果，独立建设新战斗模块，不把换引擎、移植通用插件或搭建服务器当成首版的前置条件。
